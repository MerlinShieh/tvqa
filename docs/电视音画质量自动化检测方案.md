# 电视黑屏 / 闪烁 / 卡顿 / 花屏撕裂 / 音画不同步 —— 自动化检测与测试方案（v1.1）

> **v1.2 修订（数据集驱动落地）**：工程已按本方案实现为 `tvqa` 包（2026-09-05）。
> 相对 v1.1 的实施修订：
> 1. **数据集驱动验证**：input/ 提供带 manifest 真值的注入数据集（黑/白/闪/撕裂/卡顿丢帧/花屏合成 + 音画 ±5~30 帧 mp4），
>    `python -m tvqa eval` 自动跑检测 → 帧级区间匹配 → 记分卡 → HTML 报告；所有阈值收敛到 `config/profiles/eval|field.yaml`。
> 2. **闪烁检测口径修正**：中轴翻转率对非 50% 占空比失效（1/3 占空比时中轴=亮电平），
>    改为「亮度跳变率」（相邻帧亮度差计数，一个明暗周期 2 跳变），与注入规则的 flip_rate_per_sec 口径一致。
> 3. **音画同步三层落定**：L1 被动互相关仅在内容存在语义声画锚点时有效（纯 BGM 内容信息论上不可测，报告低置信）；
>    **L3 主动测试片（闪光+蜂鸣，3s 周期防混叠）为测量链路的验收与现场标定基准**，实测误差 ≤0.4 帧（含 ~12ms 固定量化偏差）。
> 4. **卡顿像素级歧义处理**：静止场景的精确重复帧与冻结不可分，引入「运动新鲜度封顶」
>    （最后明确卡顿证据 ≤ 最后运动帧 + 武装超时）防事件无限拖长；残余误报归由系统信号归因（correlate）解决。
> 5. 撕裂检测量为「上下行带帧间位移差」（对齐数据集逐帧变位移注入）；扫描步长须覆盖撕裂线位置（小尺度 8px 步长）。


> 硬件前提：
> - **外部观测面**：电视 HDMI 输出 → 采集卡 → PC（同时获得视频流 + 音频流，代表用户真实看到的画面和听到的声音）
> - **内部诊断面**：串口（UART，始终可用，生命周期控制主通道）+ ADB（root，Android 框架层信号）
>
> 设计基线：在现有《黑屏和卡顿检测.py》的两个检测器（黑屏状态机 + 卡顿帧差状态机）之上扩展，
> 复用其已验证的工程模式：候选→确认去抖、事件目录 + 里程碑截图、CSV 汇总、异常隔离、退出结算。
>
> v1.1 修订（针对评审意见）：
> 1. 新增**闪烁/白屏**检测器（现有黑屏 5 秒连续确认逻辑抓不到高频明暗交替，见 3.2）

## 1. 故障定义与可测指标

| 故障 | 用户感知定义 | 采集卡侧信号特征 | 串口/ADB 侧可交叉验证信号 |
|---|---|---|---|
| 黑屏 | 画面全黑 ≥ N 秒 | 平均亮度 ≤ 阈值 且 黑像素占比 ≥ 95%，持续 | `dumpsys display` HDMI/显示状态、logcat HDMI handshake、串口 dmesg |
| 白屏 | 画面全白 ≥ N 秒 | 平均亮度 ≥ 高阈 且 白像素占比 ≥ 阈值，持续 | 同上（多为信号/驱动初始化异常） |
| **闪烁** | 画面在亮/暗（或黑/白）间高频往复 ≥ N 次/秒 | 亮度符号翻转率异常（帧级采样才可见） | 背光/电源驱动日志、HDCP 反复认证、内核 HDMI 重训练 |
| 卡顿/冻结 | 运动中画面停滞或跳帧 | 帧间近似重复段、重复帧比例异常（现有逻辑） | SurfaceFlinger present 延迟、`media.metrics` 丢帧、Choreographer skipped frames |
| 局部花屏 | 画面局部块状损坏/色噪 | 块效应突增、局部冻结-全局运动矛盾、梯度方向异常 | 解码器错误日志（MediaCodec/OMX error） |
| 撕裂 | 画面出现水平位移断层 | 同一帧内上下两段内容水平错位 | 通常无框架层信号，串口 dmesg（HDMI 链路）辅助 |
| 音画不同步 | 声音与画面事件错位 ≥ 感知阈（**多为持续性**） | 视频事件流与音频事件流的统计偏移 | `dumpsys audio`、音频 underrun、`media.metrics` av-drift |

感知阈值参考：音频滞后视频 > 45ms 可被察觉、> 125ms 严重（ITU-R BT.1359）；黑屏/白屏确认沿用 5s/10s 分级；闪烁确认标准建议 ≥2 次翻转/秒持续 ≥0.5s（可调，见 3.2 风险讨论）。

模块划分（每个检测器独立开关、`safe_process` 包装、互不影响——沿用现脚本约定）：

1. `CaptureSource`：采集卡视频线程 + 音频线程 + 设备健康监控（掉线、分辨率/时序变化）
2. `LumaAnomalyDetector`（黑屏/白屏/闪烁统一）：黑屏沿用现逻辑并增强（帧级发现、无信号 vs 黑内容）；白屏对称实现；**闪烁为独立高频规则**
3. `StutterDetector`：现有实现 + 系统侧证据归因
4. `CorruptionDetector`（新）：花屏（块效应/局部冻结）+ 撕裂（水平断层）
5. `AVSyncMeter`（新）：三层音画同步测量（3.6）
6. `DeviceProbe`（新）：**串口 + ADB 双通道**系统信号采集、校时、生命周期控制（3.7）
7. `EventCorrelator`（新）：跨面事件融合与归因
8. `Reporter` + `TestRunner`：输出结构与用例编排

## 3. 各检测模块详细设计

### 3.1 黑屏（增强，改动小）

现有逻辑保留（1s 采样、5s 确认、10s 严重、里程碑截图）。两个增量：

- **无信号 vs 黑内容**：采集卡时序层（`cap.grab()` 失败率、分辨率/帧率变化、锁定状态）+ 串口 dmesg / `dumpsys display` HDMI out 状态联判。黑屏事件若伴随信号断开/重握手，类型记 `SIGNAL_LOSS`，否则 `BLACK_CONTENT`。
- **帧级发现**：主循环每帧算一个极廉价指标（32×18 缩略图平均亮度），骤降即进入确认状态机——把黑屏的**发现**粒度从 1s 提到帧级，确认粒度不变。这个每帧亮度序列同时是 3.2 闪烁检测的输入。

### 3.2 闪烁与白屏（新规则，回答评审问题 1）

**为什么现有黑屏逻辑抓不到闪烁**：三重失效——(a) 1s 采样对 2Hz 以上往复产生走样，可能全部采到亮帧；(b) 明暗交替导致黑屏"连续时间"永远攒不到 5s，只会不停打"候选恢复"日志；(c) 白屏方向完全未实现。

**设计**：统一在每帧亮度序列 `luma_seq` 上做滑动窗口统计（320×180 分析帧本来就有灰度均值，复用现脚本 15fps 分析节拍即可覆盖 0.5~7Hz 的可见闪烁；30fps 全帧亮度兜底高频）：

- **白屏检测**：黑屏判定的镜像——平均亮度 ≥ `WHITE_BRIGHTNESS_THRESHOLD`（建议 235）且高亮像素占比 ≥ 95%，走与黑屏相同的 5s 确认/里程碑截图/CSV 状态机（`LumaAnomalyDetector` 参数化极性，一个类覆盖两种故障）。
- **闪烁检测**：窗口内以亮度中位数为轴，统计**符号翻转次数**（连续同极性计数一次，且单次偏离幅度 ≥ `FLICKER_AMPLITUDE_MIN` 才算一次有效翻转，滤掉正常内容的小亮度波动）。翻转率 ≥ `FLICKER_MIN_RATE`（建议 2 次/秒）且持续 ≥ `FLICKER_MIN_SECONDS`（建议 0.5s）→ 事件。事件截图保存翻转波形图（亮度-时间折线标注翻转点），这是人眼复核闪烁最直观的证据形式。
- **与卡顿互斥**：闪烁窗口内翻转率高、与"重复帧冻结"特征天然互斥，无需特殊处理；但黑闪（每次翻转都触黑阈）会与黑屏候选反复交叉，闪烁事件成立时抑制黑屏候选计时，避免同一故障出双事件——在 EventCorrelator 里做同源合并。

### 3.3 卡顿（复用 + 归因升级）

视觉层完全复用现有 `StutterDetector`（motion arming、连续重复 0.5s、6s 窗口、10s 静默恢复、结束时间反推）。升级点全在归因：事件确认后从 `DeviceProbe` 环形缓冲取事件窗内的 `logcat` jank（Choreographer skipped、BufferQueue）、`media.metrics` 丢帧增量、SurfaceFlinger present 间隔，分类为 `SYSTEM_RENDER_STUTTER` / `CAPTURE_PIPELINE_SUSPECT` / `SIGNAL_RENEGOTIATION`（有 HDMI 重握手证据时）。把现脚本"回避采集卡异常"的保守策略升级为"能区分就下结论，不能区分就标注存疑"。

### 3.4 花屏与撕裂（新模块，先规则后 AI）

在现有 320×180 signature 分析帧之上加**块级**分析（16×9 或 20×11 网格），成本可控：

**(a) 块级重复/运动矛盾图——抓局部花屏/局部冻结**：每块算与上一帧 mean diff 得 `block_diff_map`。正常视频 diff 分布连续；局部损坏表现为**整帧有运动但某连通区域持续与上一帧完全一致（冻结块）或持续高频噪声且呈网格分布**。连通异常区域 ≥ M 块且持续 ≥ 0.4s → 事件。保存异常区域高亮 mask 图（画在原始帧上），既是人眼复核证据也是未来训练数据。

**(b) 块效应（mosaic/compression artifacts）**：比较 8/16 像素网格边界梯度能量与块内梯度能量之比 `blocking_metric`，滑动基线 + 相对增幅判定，自适应不同内容。

**(c) 撕裂（tearing）**：对降采样灰度图做上/下行带水平位移估计（一维块匹配 ±8px），两行带位移差 > 2px 且存在水平长直断层线 → 撕裂候选；连续 ≥2 帧或窗口内 ≥3 次 → 事件，标注撕裂线位置截图。撕裂多由链路而非电视渲染造成，必须与采集时序事件、串口 dmesg 联合归因。

**(d) 语义级异常（UI 错乱、乱码、加载失败图）——二期**：先用 (a)(b)(c) 攒标注截图形成自有数据集，再训练轻量模型；无数据不上模型。

### 3.5 事件融合 / 归因

规则表驱动（输入：带统一时间戳的图像/音频/串口/ADB 事件流，输出主因 + 证据清单）：

| 同时窗组合 | 归因 |
|---|---|
| 黑屏/白屏/闪烁 + 串口 HDMI 断开或重训练 | 信号链路问题（非电视渲染） |
| 卡顿 + SF/Choreographer jank | 电视系统渲染问题 |
| 卡顿 + 解码错误日志 | 电视解码问题 |
| 卡顿 + 仅读取间隔异常 + 系统侧正常 | 采集/PC 链路问题 |
| 花屏/撕裂 + 解码错误 | 电视解码输出损坏 |
| 撕裂 + 采集时序变化 + 系统侧正常 | 链路/采集问题 |
| 闪烁 + HDCP 反复认证 / 背光驱动日志 | 电视固件/驱动问题 |
| AV 偏移跳变 + 音频 underrun | 电视音频管线问题 |
| AV 偏移持续同向增大 | 时钟漂移（标注容忍或上报，按产品规格） |

### 3.6 音画不同步：三层测量体系（回答评审问题 2）

评审意见正确：不同步是**持续性**问题，人工方法本质是"挑一个声画锚点对，切帧比对"。自动化不需要一开始就上模型——把人工方法拆成可计算的等价物：

**L1 连续统计层（默认常开，无模型）**——"锚点对"的通用自动化等价物是**镜头切换流 vs 音频起始流**：
- 视频事件：镜头切换检测。复用卡顿模块已有的每帧 mean_diff/changed_ratio——切换瞬间是全片最显著、时间戳最精确的视频事件（精确到帧），普通内容每分钟几十次，不需要"理解画面里的动作"。
- 音频事件：分帧频谱通量/RMS 起始点（关门、爆炸、乐句起音都是 onset）。
- 两列事件流做滑窗互相关（如 60s 窗），**中位偏移即当前 AV offset**，持续输出偏移时间序列。
- 判定持续性故障：偏移分布中位数连续 N 分钟 > 阈值（45ms 轻度 / 125ms 严重）即告警——天然匹配"不同步是持续问题"的特性，且对单点误检鲁棒。
- 局限（如实声明）：对话口型这类"无全局亮度/声像变化的细微动作"，L1 抓不到锚点；但口型不同步的片子必然也有大量场景/音频边界事件，L1 用粗锚点判"有没有问题"足够，判"多严重"交给 L2。

**L2 片段精测层（按需触发，引入模型）**——这是人工"挑张口说话+切帧"的直接自动化：
- 触发：L1 报警时、场景回归时、或每日定时采样对话密集片段。
- 做法：截取事件前后 10~20s 音视频片段，跑 **SyncNet 类唇音同步模型**（音视频嵌入对齐，可估计亚帧级 offset，有开源实现与预训练权重）→ 输出精确偏移与置信度。
- 只在片段上离线计算（可延迟批处理），不进实时主循环，规避实时性风险。
- **回答"是否需要模型定位图像动作"**：连续监测不需要（用 L1 统计锚点）；细微动作级别的精测才需要模型，且用的是唇音同步专用模型而非通用动作识别——我们不需要知道"画面里是什么动作"，只需要两侧时间事件的精确对齐。

**L3 主动标定层（测试场景用）**：ffmpeg 合成「闪光+蜂鸣」标记对测试片，测端到端绝对偏移。作用：① 标定采集链路自身的固定偏移基线（L1/L2 都以此为 0 点）；② 场景切换前后（换源、待机唤醒、升级后）回归测试。

**复核工具（贴合现有人工流程）**：任何 AV 事件自动生成"复核包"——带帧号时间戳的片段视频 + 对齐到同一毫秒栅格的音频波形图 + L1/L2 估计值标注，人工只需播放确认，省去手动切帧定位的时间。

### 3.7 DeviceProbe：串口 + ADB 双通道（回答评审问题 3）

评审明确了串口始终在场且 ADB 是"远程操作"（需要开关 adbd 等前置）——据此把串口定为**控制面主通道**：

**串口通道（pyserial，波特率按机型配置）**
- **日志源**：全程落盘（内核 dmesg、HDMI/CEC/驱动报错、uboot/bootloader 输出）。关键价值：ADB 不存在的时段它仍在——开机过程、待机唤醒、kernel panic/reboot、adbd 未起或崩溃期间。现方案归因需要的 HDMI 链路底层事件大多只在串口日志里有。
- **控制面**：生命周期命令走串口：开启 adbd、重启、待机/唤醒、恢复出厂、厂商测试指令。测试编排层的"前置状态建立"全部经串口，不依赖 ADB 先活着。
- **失联判读**：`ADB_LOSS` 时对照串口日志区分"电视真重启/崩溃"（串口有 boot 日志）vs "USB/网络通路问题"（电视侧一切正常）——这是单独 ADB 通道做不到的。
- **风险**：各机型 console 格式不一（需登录、prompt 各异、输出乱序交叉）。对策：控制命令实现为"发送 + prompt/回显匹配 + 超时重试 + 人工可注入"的弱约定层，换机型只改配置不改代码。

**ADB 通道（root）**
- 框架层信号照旧：`logcat -v epoch` 流式（Choreographer/MediaCodec/AudioTrack/HDMI/CEC tag 过滤）、`dumpsys display/audio`（1s 快照）、`dumpsys media.metrics` + `gfxinfo framestats`（10s）。
- 交互层命令（UI 操作 `input keyevent`、起应用 `am start`）由测试编排层调用。
- 校时：每 30s `adb shell date +%s.%N` 与本地配对采样，滑动拟合偏移+漂移率，把 ADB 时间戳折算到 PC monotonic 轴；串口侧事件用串口服务器时间戳与 PC 落盘时间对齐。

**公共要求**：环形缓冲保留最近 5 分钟信号 + 原始日志滚动落盘；事件发生时自动裁剪前后 10s 切片（logcat + 串口双份）入事件目录；每通道独立线程、断线指数退避重连，任一通道故障只降级归因能力、绝不影响图像检测主流程。

## 4. 自动化测试编排（用例层）

用例 = `前置状态（串口命令）→ 操作序列（ADB keyevent / am start）→ 观察窗口 → 断言`：

| 场景族 | 示例用例 | 重点断言 |
|---|---|---|
| 启动 | 冷开机（串口触发）→主页→各预装应用 | 启动期黑屏/白屏/闪烁、首帧渲染时间、串口 boot 异常 |
| 播放 | 本机播放器播 4K/高码率/长视频、快进切流 | 卡顿、花屏、L1/L3 音画偏移 |
| 输入切换 | HDMI1↔HDMI2↔TV 源 循环 ×N | 黑屏时长、撕裂、`SIGNAL_LOSS` 归因、切换后 L3 基线回归 |
| 交互 | 菜单连续操作、音量/频道、投屏 | 交互卡顿、"按键(ADB注入时间戳)→画面响应"延迟量化 |
| 电源 | 待机↔唤醒循环 ×N（串口控制） | 唤醒白屏/闪烁/黑屏、串口侧 resume 错误、唤醒后 L3 回归 |
| 稳定性 | 循环播放+周期操作，4~24h | 全类事件汇总、偏移漂移趋势 |

输出 `test_report.csv`：每用例一行（通过/失败、各检测器事件计数、事件目录链接）。失败阈值集中在配置表，按产品规格改。

## 6. 实施路线图

**Phase 1（地基，约 1.5~2 周）**
- 采集卡音频流接入（sounddevice/WASAPI，设备枚举与基线延迟实测）；主循环视频+音频双线程化
- `DeviceProbe`：串口通道（日志落盘+控制命令层）+ ADB 通道（流式/快照/校时/环形缓冲）
- 现脚本重构为包结构（detectors/ probe/ capture/），修 BOM bug
- 验收：拔掉 USB 线重启电视的测试中，串口日志完整捕获 boot 过程，事件目录里图像事件+双通道日志切片时间轴对齐

**Phase 2（亮度类故障 + 花屏撕裂规则层，约 2 周）**
- 黑屏帧级发现+信号归因；白屏检测器；**闪烁检测器**（翻转率+波形截图+与黑屏同源合并）
- `CorruptionDetector` 三项（块级矛盾/块效应/撕裂）
- 人工制造坏样本（拔插 HDMI、遮挡、损坏媒体文件、调低帧率源）标定阈值
- 验收：闪烁样本召回，正常内容 2h 零误报（黑/白/闪合计）

**Phase 3（音画同步，约 2~2.5 周）**
- L3 先行（它定义 0 点）：测试片生成+偏移估计+基线标定
- L1：镜头切换检测复用卡顿统计、音频 onset、滑窗互相关、偏移时间序列与持续超阈告警
- L2：SyncNet 类模型选型（开源实现跑通、在自有片段上验证精度），事件触发式精测 + 复核包
- 验收：注入已知偏移（±80/150ms）样片，L1 判"有问题"、L2 测得值误差 ≤ 一帧（33ms）

**Phase 4（编排与归因，约 1.5~2 周）**
- EventCorrelator 规则表落地；用例 YAML + 执行器（串口前置 + ADB 操作）+ `test_report.csv`
- 长跑模式与断点续测
- 验收：一条命令跑完「冷开机×3 + 输入切换×50 + 4K播放30min + 待机唤醒×20」出带归因的报告

**Phase 5（可选，数据驱动）**
- 语义级花屏/UI 错误模型训练（依赖 Phase 2 起的标注截图积累）；L2 精测模型的领域微调（如新闻播报场景口型数据）

## 7. 风险与待确认问题（需要继续沟通的点）

1. **闪烁的检测频率上限**：30fps 采集只能分辨 ≲10Hz 的可见往复，且存在走样风险。待确认：你们要测的闪烁典型频率范围？若是背光 PWM 类人眼不可见的高频闪，采集卡方案测不了，需光电二极管/高速相机另案。建议阈值先用"翻转率 ≥2/s 持续 ≥0.5s"起步，试运行期只记录不告警标定。
2. **白屏内容误报**：雪地/白底广告可能触发高亮判据，靠"95% 高亮像素占比"过滤，需实际片源验证；建议白屏确认时间起步 3s。
3. **L1 对少切换内容失效**：单镜头长内容（体育直播固定机位）锚点稀疏，置信度会显著下降——设计上偏移序列带 confidence 字段，低置信时段自动降级为"仅趋势监控"，报警依赖 L2 精测。
4. **采集链路固定偏移**：采集卡音频通路相对视频通路的固有延迟未知，L3 基线标定为必做第一步；且注意电视若经内部处理链路回环（HDMI-in→out），绝对偏移含电视处理延迟固定项，报告需注明测量口径。
5. **串口机型差异**：console 是否需要登录、波特率、有无 root shell 输出，各平台不一——Phase 1 需要一台目标机型配合实测后固化配置。
6. **采集卡自证健康**：一切归因的前提。长跑前先空跑 2h（已知正常源直连），确认无自发异常。
7. **误报管理纪律**：所有新检测器先"只记录不告警"跑一周看事件分布再定正式阈值；同源合并规则（闪烁 vs 黑屏候选）需联调验证不吞事件。
8. **CPU 预算**：每帧 32×18 亮度 + 15fps 块级统计 + 音频 RMS + 撕裂行带搜索，预估普通 PC <15%，撕裂搜索若超预算降频到 7.5fps；L2 模型离线批处理不占实时预算。
